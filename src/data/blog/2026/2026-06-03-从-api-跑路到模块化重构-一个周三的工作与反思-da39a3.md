周三过得很密。早上配了四个 GO Skill 到 Content Research agent，下午参加销售培训，晚上发现色卡渲染 API 跑路。一天之内踩了三个坑，也逼出了三个反思。

## 上午：把姚金刚的 GO Skill 落到了 agent 上

之前一直在研究 GEO（生成式引擎优化），但都是零散地试。今天一口气把姚金刚的四个 GO Skill 配置进了 Content Research 的 Hermes Profile：

- **品牌实体 GO 鉴别 skill** — 判断品牌在 AI 搜索结果里的存在感和可见度
- **GO 标题生成 skill** — 针对不同搜索场景生成 AI 友好的标题
- **GO 科普内容生成 skill** — 这个最实用：指定平台（官网、公众号、小红书、抖音）就能输出对应风格的文案，包含摘要、正文题目、FAQ、术语表

这些输出直接就能进知识库。比如 skill 自动提到了「金属膜会不会影响车机信号」——这类话题有待核实，但至少它知道该问什么。还自动生成了「金属膜和陶瓷膜的区别」的 prompt，后续可以直接作为选题展开。

## 下午：销售培训的锚点效应和反问法

销售培训里印象最深的是两个点：

1. **锚点效应**：先报高价产品，再推性价比款，客户心理锚点被拉高后会觉得「还不错」。反过来，如果客户带着 199 元套餐进来就问价，你不能一上来就夸自己产品多好，而是要先确认他的核心需求——他来贴膜是因为**隔热**，不是因为他想买 199 元的东西。

2. **反问法**：把思考的球抛回给客户。不要替他做判断，让他先明确自己的需求，你才能精准安利。这跟做产品需求调研是一样的逻辑。

## 晚上：API 跑了，但我的代码结构也该跑了

开完会发现最大的事：色卡渲染用的中转 API 跑路了。只剩 5 天时间。

我第一反应是懊恼：明明知道中转站容易跑路，为什么只挂了一家？没有任何备选方案。

但这个锅不全在外部。我复盘了一下色卡渲染那块的代码——700 多行一个函数，模块边界模糊到我自己改起来都费劲。这对非专业编程出身的人来说实在太不友好了。

所以琢磨出一个想法：把 skill 的编写当作**项目来管理**。

- v1：MVP，先跑通核心逻辑
- v2：模块化拆分，别把所有东西塞进一个函数
- v3：插件式挂载，换 API 就像插拔零件，而不是改核心代码

核心逻辑其实很简单：色卡 → 注入提示词 → 生成图片 → 保存 → 飞书返回。是迭代中堆起来的细节把代码撑胖了。

## 明天的计划

1. **GEO 科普内容生产** — 知识大盘点，先把选题库跑起来
2. **色卡渲染** — 换 API + 用项目迭代思维重构代码
3. **官网筹备** — 尽早建，不要拖
4. ~~公众号~~ — 改名敏感期，先停发

今天就这样。API 可以跑路，但项目迭代的思维不会。
